01배경 · 목표

추천 품질을 좌우하는 맛집 데이터의 SQL 쿼리 관리

다인원 맛집 추천 서비스(요기잇)의 맛집 데이터를 SQL 쿼리로 직접 관리하고 있었습니다

NEXTERS에서 만든 다인원 맛집 추천 서비스 요기잇은 추천 품질이 맛집 데이터에 좌우됩니다. 이 데이터를 DBeaver에서 SQL 쿼리를 작성해 관리했고, 하나를 고칠 때마다 쿼리를 짜야 했습니다.

쿼리는 노션 문서로 따로 정리해 관리했지만, 맞는 쿼리인지 매번 다시 확인해야 했고 새로 보고 싶은 데이터가 생기면 백엔드 개발자에게 여러 번 물어봐야 했습니다.

서비스 확장으로 지역을 늘리고 맛집을 직접 큐레이션하는 운영이 시작되면서, 쿼리 없이 관리할 방법이 필요해졌습니다.

02문제 정의

개발자 문의에 의존한 데이터 확인과 배포 후 오류 대응

보고 싶은 데이터를 확인하려면 쿼리 확인과 개발자 문의가 필요했고, 새 지역·맛집은 운영 배포 후에야 오류를 발견했습니다

  • 노션에 정리한 쿼리가 맞는지 매번 재확인
  • 새 쿼리가 필요하면 백엔드 개발자에게 여러 번 문의
  • DBeaver 조작이 익숙하지 않아, 탭 하나에서 막혀도 개발자를 호출
  • 새 지역·맛집 데이터는 운영 배포 후 틀리면 급하게 대응

개발자가 아니어도 데이터를 보고 반영할 수 있는 화면이 없는 것이 원인이었습니다.

03가설

어드민 확인과 검수 후 노출을 통한 쿼리 없는 운영

어드민에서 데이터를 바로 확인하고, 새 지역·맛집은 앱에 보이지 않는 상태로 검수한 뒤 노출하면 쿼리와 개발자 문의 없이 운영할 수 있을 것이라 보았습니다

04액션

기능 정의서 작성과 운영 요청 기반의 기능 확장

반응형 어드민의 기능을 정의하고, 운영하며 필요해진 기능을 요청해 확장했습니다

  • 맛집 데이터 수정·관리와 동기화, 모임 데이터 조회, 모바일에서도 관리 가능한 반응형 구성
  • 지역 추가 어드민: 지역별로 앱에 노출할지 선택하는 활성화 여부를 두어, 새 지역을 어드민에서 먼저 검수한 뒤 공개
  • 맛집별 노출/비노출(기본값 노출): 삭제 대신 숨김 처리로 운영
  • 모임 대시보드: 모임이 언제, 몇 명, 어느 지역에서 열렸는지와 일별 모임 생성 추이를 확인
  • 맛집 추가 시 대표메뉴 가나다순 정렬, 닉네임과 추천 이유를 어드민과 UI에 추가하도록 요청
  • 팀원이 각자 맛집을 등록할 때 쓸 닉네임 정책(에디터, 메이커, 요기잇's Pick) 논의
  • 자연어 DB 조회툴은 팀 역량 이슈로 어려워, 주기적으로 조회하는 쿼리를 어드민에 넣는 방향으로 정리

어드민은 Codex로 만들었고 피그마에 정리한 디자인 시스템을 연동했습니다. 제작은 팀 백엔드 팀원이 했고, 저는 기능 정의서를 작성하고 디자인 시스템을 제공했습니다.

05결과 · 해석

SQL 없이 지역 추가와 맛집 노출 운영

어드민에서 지역 추가와 맛집 노출 제어를 쿼리 없이 처리하게 됐습니다

  • 지역 추가 어드민 개발 완료, 지역별 활성화 여부 선택
  • 맛집별 노출/비노출 제어와 노출 여부 목록 확인 요청
  • 모임 대시보드로 집중할 지역과 시간대별 이용 흐름을 한눈에 확인, 마케팅 집행 중 조회수·전환율이 변하면 어떤 마케팅 때문인지 시점별로 확인
  • 정량 수치는 측정하지 않아 성과 수치로 쓰지 않습니다.
06레슨런

반복 빈도를 기준으로 정하는 어드민 범위

운영 중 요청이 계속 쌓이는 상황에서는, 모든 요청을 화면으로 옮기기보다 반복해서 실행하는 쿼리부터 어드민에 넣어 범위를 정해야 한다는 점을 배웠습니다.

앞으로는 기능을 정의하기 전에 어떤 쿼리를 얼마나 자주 실행하는지 먼저 기록하고, 반복 빈도가 높은 것부터 화면으로 옮기겠습니다.
